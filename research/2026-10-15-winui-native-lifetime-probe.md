# WinUI native tray and window lifetime feasibility

- **Date:** 2026-10-15
- **Author:** Codex

## Problem

The stationary WinUI candidate must prove native tray callbacks, owned menus, nonactivating bubble mouse input, dismissal and resource cleanup before production extraction. Successful XAML startup does not establish these behaviors.

Cause of processing delay and app cadence inside the gap remain unknown. Keep early-readiness hygiene and processing-loss diagnosis categorized for later separate scopes, with existing instrumentation and unchanged acceptance. No new experiment, integration or product code. Detailed derived values: `artifacts/winui-rebuild/m02/r2c-retained-coverage.json`.

- Register an icon with Shell_NotifyIcon and explicitly set version 4 after every add. Version-4 callbacks encode the event in the low word of lParam and identifier in the high word; NIN_SELECT/NIN_KEYSELECT cover mouse and keyboard. Do not also toggle on button-up.
- Explorer sends TaskbarCreated to top-level windows. Use the existing WinUI HWND as the receiver, re-add only this prototype icon, and never restart Explorer to test it.
- A native shortcut menu needs a foreground owner and the documented WM_NULL follow-up. Scope menu ownership so deactivation during its modal loop does not dismiss the flyout. TrackPopupMenuEx returning zero can mean cancel, not a Win32 error by itself.
- Show(false) avoids show-time activation. WS_EX_NOACTIVATE and MA_NOACTIVATE address mouse-down activation too. Returning MA_NOACTIVATE preserves the click; MA_NOACTIVATEANDEAT would discard it. A bubble click then explicitly activates the flyout.
- SetWindowSubclass delegates must remain alive until removal; use the same dispatcher thread. Remove hooks and the icon before closing the windows.

Documentation supplies contracts, not proof of this implementation's focus or presented frames. Tests must observe real input and foreground HWND, and distinguish synthetic message coverage from actual Explorer input.

## Alternatives considered / chosen approach

Use CsWin32 with the existing WinUI pump, a native menu, one probe flyout and one nonactivating 32-DIP bubble. Keep synthetic flags and no ADB/preferences/production mutex. Reject WinForms product hosting, a tray wrapper dependency, an extra message-only product window, broad global hooks and timer-based focus polling. Test-driver waits are bounded and do not drive production animation.

## Compatibility concerns

Explorer recreation, packed callback coordinates on negative monitors, DPI changes, modal menus and foreground-lock restrictions require explicit observations. System-shared stock icons must not be destroyed. A canceled menu is not a failure; failed registration, subclassing or cleanup must be reported. The resource ceiling approved today is 200 MiB for the complete future app, not an allowance for this probe alone.

## Testing implications / open items

Exercise menu cancel/selection, mouse and keyboard tray callbacks, hidden receiver recreation, pin/deactivation/Esc, actual bubble mouse-down without focus theft, hide-time progress settlement, and bounded owned-process cleanup. Actual Explorer restart and unavailable DPI hardware remain unexercised unless observed. ETW presentation still requires a permitted Windows token; native message counters are not a substitute.
